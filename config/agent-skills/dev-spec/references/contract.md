# Spec quality bar

Use the authoring command schema for exact fields. Keep the spec small enough to review, but complete enough that approval has observable meaning.

- Identify the feature, actors, outcome, scope, exclusions, constraints, and verified current behavior.
- Give each requirement a stable ID and each requirement observable Given/When/Then acceptance. Preserve IDs when revising the same obligation.
- Mark assumptions and their basis. Keep consequential unanswered behavior questions open; defer only implementation questions to planning.
- Add domain, workflow, or contract artifacts only when useful. Diagrams are raw Mermaid. Cite inspected source and relevant pinned memories; never invent source handles or graph anchors.
- Record material alternatives and rationale as durable authoring content. Separate verified facts, user decisions, and proposals.

Validation establishes structure, coverage, link integrity, and evidence freshness; it does not prove that the proposed behavior is correct. Read the rendered acceptance packet before requesting approval. Confirmation applies to the exact intent digest; semantic changes require renewed approval. A reviewer cannot approve on the user's behalf.

Save a meaningful private draft before pausing, then verify readback. Desktop draft durability does not imply readiness. Personal cloud drafts are task-local and may not outlive the task. Publication requires a concrete preview, explicit approval of that exact publication, and verified readback. Never archive unrelated memories or treat local files as authoritative receipts.
