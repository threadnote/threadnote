# Cycle state and snapshots

Use cycle state as authority. Start or resume the exact run and generation, verify checkout identity and source head, then inspect current plan and phase state. Never overwrite or reinterpret incompatible state; recover only the missing dependency.

Capture immutable source snapshots through actions. Keep the review base fixed, distinguish pre-existing changes, and reconcile staged or uncommitted source without staging it as a side effect. Unmerged state, dirty submodules, missing objects, or mismatched heads are blockers to resolve explicitly.

The coordinator alone advances iterations and phases. Preserve prior validation, review, and delivery evidence. Any source drift invalidates verdicts that covered the changed source. Use final combined-tree validation for final acceptance.

If interrupted, resume from the last verified receipt. Do not blindly repeat a write, regenerate a completed snapshot, delete receipts, or reuse stale review summaries. Report identity or recovery conflicts rather than bypassing them.

Each run has a profile. `standard`, the default for new runs, is strict only about business intent and review integrity: changing requirements, acceptance or the delivery target needs a confirmed intent, and every delivered tree needs validation of that exact tree plus a review of it under the same intent, or an audited review waiver. Ownership is derived: a file outside the planned paths is a `scope.out-of-plan` warning, and a path-only plan edit needs no new confirmation. A path-only reconcile leaves every phase as it is: a validated, delivered or merged phase keeps its proof, and its dependents stay untouched. A moved declared base records a new snapshot of the same tree, which the review of that tree still covers. A standard run records source only with `record-snapshot`; the strict recovery commands refuse. Runs created before profiles, and runs switched with `task-action set-profile --profile strict` (MCP `workflow_task_control` command `set-profile`), keep every earlier bookkeeping gate. Loosening a run to `standard` needs the user's own authority statement.

Every refusal returns `gate`, `detail` and `next`; run the named next command instead of guessing a recovery: `next.arguments` is the input for the MCP tool `next.tool` and `next.cli` is the CLI line, with `<placeholder>` values to fill. When the validated source or its base changed on a deliver card, the refusal names `reopen`; resume the phase and record a new snapshot. When a missing reviewer or a tool defect blocks `review.required` or `review.blocking`, ask the user and record `task-action waive --gate <id> --reason <text> --user-authority <quote>` for the current tree; no other gate takes a waiver. Waivers exist on every profile, strict included. A waiver covers only that tree under its intent, and a `review.blocking` waiver only the findings of the review it accepted. Delivery results list every waiver and name the covering one (`coveringWaiverId`), closeout documents mark it, and no waiver covers an intent change.
