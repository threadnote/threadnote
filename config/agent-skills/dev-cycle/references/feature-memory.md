# Feature memory and publication

The change author owns shared feature memory. Before a substantive PR, refresh the durable feature memory with the complete rationale, considered alternatives, actual implementation, and current code evidence. Read the full result back and verify it against the source. Existing authorization to share persists; do not ask again when it already covers this action.

An independent code reviewer of someone else's PR must not draft, publish, or prompt to share that feature's memory (including "which team?" selection). Review may _recall_ shared knowledge for alignment; publication stays with the author, who has the landing contracts and can refresh when addressing review feedback.

Keep memory private unless publication is authorized. For personal cloud, work remains task-local until a concrete publication preview receives explicit approval and verification succeeds. Do not publish raw private planning records.

Update linked knowledge through workflow actions. Preserve stable identities and history; retire only artifacts the current run owns, and only after independent final readback.
